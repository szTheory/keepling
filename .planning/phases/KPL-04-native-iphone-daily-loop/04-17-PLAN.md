Assemble the full gate in `tooling/verify-ios-phase.mjs`. Running it with no arguments runs every lane discovered under `tooling/ios-lanes/` and prints one `LANE name=… status=… cases=… duration_ms=… input_digest=… seed=…` line each, then a summary line reporting the lane count and the failure count, and exits non-zero if any lane failed.

Inherit the desktop gate's exact anti-vacuity contract, and make its refusals explicit rather than implied:
- A lane whose child process exits non-zero fails.
- A lane whose parse function throws fails.
- A lane whose parse function returns zero, a non-finite value, or a negative value fails.
- A lane definition file that fails to load fails the whole run, because a lane that cannot load is indistinguishable from a lane that was quietly deleted.
- A lane present in the requirement map but absent from `tooling/ios-lanes/` fails the whole run.
There is no assume-it-passed fallback anywhere in this file.

Add the device-lane binding rule: the `device` lane is bound to a specific `KeeplingBuildDigest`, and the gate refuses to report success if that lane's recorded evidence names a different digest than the current build manifest, or if the evidence is missing, stale, or partial. This is the Phase 3 macOS-integration binding pattern carried forward with attestation in place of a packaged-artifact digest, and Phase 3's own experience is the reason it must be a loud failure and never a skip.

Add a `--requirements` check: declare the map from each phase requirement — IOS-01, IOS-02, IOS-03, IOS-04, and the SRV-02 iPhone adapter proof — to the lanes that prove it, and fail if any requirement maps to no lane or maps to a lane that does not exist. Read the requirement ids from `.planning/REQUIREMENTS.md` rather than hard-coding them, so a requirement added later without a lane fails this check.

Create `tooling/ios-lanes/README.md` documenting the lane contract: what a lane file must export, that its parse function must throw rather than return zero on unparseable output, and that a lane is added by adding a file and never by editing the runner.

Add the root script `verify:ios:phase` if Plan 04-01 has not already added it, and confirm no iOS script delegates through pnpm into `apps/ios`.

Prove the gate is not vacuous by breaking it deliberately during development: make one lane report zero cases and confirm the run fails, and point one lane at a nonexistent test target and confirm the run fails. Record both in the SUMMARY. A gate nobody has watched fail is a gate nobody should trust.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Lane output -> phase acceptance claim | The gate's parse layer is the only thing between raw child output and a green phase. |
| Device-lane evidence -> the build under test | Evidence bound to a different build is a false claim about the shipped artifact. |
| Disclosure text -> the reader's interpretation of a checkmark | An unstated limit is read as coverage. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-17-01 | Repudiation | A skipped or zero-case lane reported as a pass | high | mitigate | The gate fails on zero, non-finite, negative, unparseable, and unloadable lanes, each proven by a deliberate break recorded in the SUMMARY (D-24). |
| T-04-17-02 | Repudiation | Device evidence reused across builds | high | mitigate | The gate refuses when the device lane's recorded `KeeplingBuildDigest` differs from the current build manifest, or when the evidence is missing, stale, or partial. |
| T-04-17-03 | Repudiation | A requirement with no proving lane counted as covered | high | mitigate | `--requirements` reads the ids from `.planning/REQUIREMENTS.md` and fails on any unmapped requirement or any mapped-but-missing lane. |
| T-04-17-04 | Spoofing | A checkmark read as more coverage than it provides | high | mitigate | The consolidated disclosures table states, per claim, what is proven and by what, and what is explicitly not proven. |
| T-04-17-05 | Tampering | A lane silently deleted from the glob directory | high | mitigate | The requirement map names its lanes, so a deleted lane file fails the run rather than reducing the lane count quietly. |
| T-04-17-06 | Elevation of Privilege | Phase acceptance depending on CI that has never run | medium | mitigate | Every lane is Mac-local tooling invoked directly; the gate has no CI dependency, per D-24 and O-35. |
| T-04-17-07 | Information Disclosure | Provenance metadata in committed evidence | low | accept | The manifest records git revision, signing fingerprint, and profile UUID deliberately as identity metadata; no credential is recorded. |
