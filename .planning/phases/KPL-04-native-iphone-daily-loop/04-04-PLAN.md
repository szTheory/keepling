<objective>
Answer, by measurement, the one platform question that D-38 and D-40 depend on and that no amount of careful design can resolve — can the tab-view bottom accessory be genuinely absent on this Mac's pinned iOS SDK 26.5 — and produce the committed Swift design-token output every later iPhone view consumes.

Purpose: RESEARCH.md's Open Question 1 flags Apple DTS confirming there is no supported hide API as of iOS 26.1, with the exact SDK-26.5 behavior unmeasured. Planning the accessory strip on an assumption in either direction is exactly the "discovered defect mid-implementation" this phase can least afford. Both halves of this plan are enabling work every UI plan from 04-09 onward depends on, which is why they are early and parallel to the storage and reducer work.

Output: an executable measurement of accessory hostability with a named capability constant, an honestly-recorded disclosure if absence is unachievable, and a token emitter with committed Swift output.
</objective>

Build a real, committed measurement — not a throwaway spike. Add `Tests/KeeplingUITests/AccessoryAbsenceProbeTests.swift` hosting a minimal two-tab `TabView` in the app under a launch-argument-selected probe scene, and measure three distinct configurations of `tabViewBottomAccessory` on the pinned SDK:

1. **Conditional content** — the accessory modifier applied with an `if` inside its content closure that yields nothing.
2. **Conditional modifier** — the accessory modifier applied only when the state warrants it (the modifier itself absent from the view tree, not just its content empty).
3. **`isEnabled:` parameter** — the accessory modifier applied with its `isEnabled` argument false, if that overload exists on this SDK; if the overload does not exist, record that fact explicitly rather than silently skipping the configuration.

For each configuration, assert on the rendered geometry and hit-testability, never on text content. RESEARCH.md names the exact false-green this avoids: a test that only checks for empty text passes while an empty capsule visibly persists. Measure the accessory element's frame height and its hit-testable region through XCUITest's element geometry, and require both to be zero (or the element to be non-existent) for a configuration to count as achieving absence. Also record the tab bar's own top edge in each configuration so a reserved-but-invisible strip is detectable as a layout shift rather than only as a visible capsule.

Create `apps/ios/Sources/Keepling/SyncRecovery/AccessoryHostability.swift` declaring a named capability value with exactly two cases — absence is achievable via a named configuration, or absence is not achievable on this SDK — plus the measured SDK version string. This constant is the single place Plan 04-10 reads to decide how to render, so the decision is one named value rather than scattered conditionals.

Then take one of exactly two paths, and record which in the SUMMARY with the measured numbers:

- **If absence is achievable in at least one configuration:** set the capability to that named configuration, and keep `AccessoryAbsenceProbeTests` as a permanent regression test asserting zero frame and zero hit region for that configuration. A future SDK that regresses this fails the suite loudly instead of quietly reintroducing ambient chrome.

- **If no configuration achieves absence:** set the capability to not-achievable, keep the probe test asserting the measured non-zero frame (so the day Apple fixes it, the test fails and prompts the upgrade), and write the disclosure into `docs/testing/ios-testing.md` in the same per-dimension evidence-table form 03-UI-SPEC adopted: what the criterion claims, what is actually proven, and what is not. The disclosure text must state plainly that the accessory reserves layout space when healthy on SDK 26.5, cite the Apple DTS forum thread and the four Feedback numbers, and name the fallback: the accessory renders as an empty, non-interactive, accessibility-hidden strip carrying no text, no glyph, and no count when the projection is healthy. Do not repurpose the reserved space into a healthy status badge — the recorded prohibition forbids exactly that, because a permanently visible synchronization indicator is the ambient-noise pattern D-40 rejects.

Create `docs/testing/ios-testing.md` as the iOS analogue of `docs/testing/desktop-testing.md`: the lane inventory, what each lane proves, and a disclosures section that this task seeds and Plans 04-13 and 04-16 extend.

Add the lane definition file `tooling/ios-lanes/accessory-probe.mjs` (the runner globs `tooling/ios-lanes/*.mjs`, so lanes are added without editing the runner).

Create `tooling/emit-swift-tokens.mjs` reading `packages/design-tokens/tokens.json` and writing `apps/ios/Sources/Keepling/DesignTokens/GeneratedTokens.swift`. The emitter is mechanical: it must not hard-code any token name or value, so a token added to the JSON appears in the Swift output without touching the emitter. Support a `--check` flag that regenerates into a temporary path and exits non-zero on any diff against the committed file, exactly as `tooling/check-contracts.mjs` does for the TypeScript client and as `tooling/generate-ios-client.mjs` does for the Swift wire client.

Emit, per the DTCG source: color tokens as light/dark pairs resolvable at runtime so a system appearance change applies while running (D-47) rather than being baked at launch; spacing tokens as point values; and typography tokens as the four declared roles mapped to iOS Dynamic Type text styles, so scaling — not a fixed point size — is the runtime contract. The four roles and their nearest system text styles are fixed by the UI-SPEC: Label to footnote/caption at semibold, Body to body at regular, Heading to title3 at semibold, Display to largeTitle at semibold. Emit exactly four roles and two weights; a fifth size is a UI-SPEC violation.

Add the iPhone density aliases the UI-SPEC declares as first-class tokens if they are not already in `tokens.json`: `layout.target` at 44 points (minimum hit target) and `layout.taskRowMin` at 52 points. If they are absent from the source, add them to `packages/design-tokens/tokens.json` so the CSS and Swift outputs stay derived from one source, and regenerate the CSS output as well; do not introduce a Swift-only literal.

Create `apps/ios/Sources/Keepling/DesignTokens/TokenSemantics.swift` as the hand-written, non-generated accessor layer: SwiftUI `Color`, `Font`, and `CGFloat` accessors named for their semantic role (canvas, surface, primary text, muted text, accent, destructive, and the spacing and layout scale), reading only from `GeneratedTokens`. Every view built in Plans 04-09 through 04-14 consumes this file, never a literal and never `GeneratedTokens` directly, so a token rename is one edit.

Add the root script `tokens:swift` invoking `node tooling/emit-swift-tokens.mjs`, following the existing script naming convention. Add the lane definition file `tooling/ios-lanes/design-tokens.mjs` (the runner globs `tooling/ios-lanes/*.mjs`, so lanes are added without editing the runner) running the emitter's `--check`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Platform SDK behavior -> product trust claim | D-38's "absent when healthy" is a trust claim about what the UI says; a platform limitation that silently defeats it turns a disclosure into a false claim. |
| tokens.json -> generated Swift -> compiled app | Generated code enters the binary; a drifted committed output ships visual intent nobody reviewed. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-04-01 | Repudiation | Accessory absence claim | high | mitigate | Task 1 measures frame and hit region rather than text content, which is the exact false-green RESEARCH.md warns about; an unachievable absence is disclosed in `docs/testing/ios-testing.md` rather than asserted. |
| T-04-04-02 | Tampering | Committed generated token output drifting from source | medium | mitigate | Task 2's `--check` flag plus the `design-tokens` lane fail on any diff between `tokens.json` and the committed Swift and CSS outputs. |
| T-04-04-03 | Information Disclosure | Probe scene reachable in a shipped build | medium | mitigate | The probe scene is selected by a launch argument used only by the UI test target; the SUMMARY records whether it is compiled out of release configurations, and if not, that it renders no user data. |
