<objective>
Close the two durability gates the tracer and Plan 04-02 left open — settlement (G8) and at-rest posture (G7) — and prove the adversarial claim D-09 rests on: even a hand-restored store cannot double-apply an accepted command.

Purpose: D-09 calls for belt and braces. The braces are backup exclusion; the belt is that server mutation-identity plus fingerprint checking makes any replay a no-op. The belt is the part that has to be proven, because it is the part that still holds when the braces are bypassed — by an iCloud restore, an iTunes restore, or a person copying a database file.

Output: the full settlement path under test, a restored-store replay fixture, the durable unit treated as one unit, and an honest data-protection disclosure split between what the simulator can prove and what only the device lane can.
</objective>

  <behavior>
    - Settling an acknowledgement whose mutation identity is in the outbox and whose fingerprint matches applies canonical state, writes the terminal outcome to the journal, recomputes the visible projection, and deletes exactly that outbox row — all recorded as one commit by the transaction hook.
    - Settling an acknowledgement whose fingerprint does not match the stored immutable command's fingerprint is refused and mutates nothing.
    - Settling an acknowledgement whose mutation identity is absent from the outbox but whose terminal outcome already matches the journal is a no-op success.
    - Settling an acknowledgement whose mutation identity is absent from the outbox and whose journal outcome differs, or is missing, is refused with a named error.
    - A `conflict` outcome writes a conflict row linked to the original receipt and applies only the affected fields the server returned; it never blanks an unaffected field and never replays the canonical shadow over the person's edit.
    - A `rejected` outcome terminalizes and deletes the outbox row without applying any canonical state.
    - Undo availability carried on a successful acknowledgement is retained rather than discarded.
  </behavior>
  <action>
Generalize the tracer's capture-only settlement in `GRDBLocalStore.swift` to the full `acknowledge` surface, mirroring the desktop `acknowledge` method's branching exactly. The branching order matters and is the source of G8's whole value: look up the pending outbox row joined to its immutable command; if absent, check the journal for an already-terminal matching outcome and treat that as a no-op success; if the fingerprint mismatches, refuse; otherwise apply canonical or conflict state, terminalize, recompute the projection, and delete the exact outbox row.

The acknowledgement validator stays strict at `accepted` and `already_satisfied` for a 200 answer — a conflict arrives as a 409 problem, and widening the validator would convert a contract violation into a silent one. The conflict path therefore enters settlement from the refusal classifier built in Plan 04-05, not from a widened success validator.

A refusal never overwrites the local row from the server's answer: a 409 carries only the affected fields, and replaying the canonical shadow would erase the person's edit while the copy still promises it is kept. Assert this with a test that edits two fields locally, receives a conflict naming one of them, and requires the other to survive untouched.

Write `Tests/StorageTests/SettlementTests.swift` first, red, covering all seven behaviors, asserting the single-transaction claim with the same GRDB transaction-completion hook technique Plan 04-02 established rather than inferring it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Device backup / restore -> app store file | A restored store carries outbox rows whose server outcomes are unknown to the restored process. |
| Account namespace fence -> restored local intent | A store restored under a different account must not push its previous account's commands. |
| iOS file protection -> store file at rest | The only at-rest control, since D-08 declines SQLCipher. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-06-01 | Elevation of Privilege | Restored backup replaying commands into a fenced account | high | mitigate | Task 2's adversarial fixture proves every restored outbox row is fenced under a different namespace and settles as `already_satisfied` under the same one (D-09). |
| T-04-06-02 | Repudiation | Duplicate acknowledgement treated as an error or double-applied | high | mitigate | Task 1 proves a replay is a no-op success with full table snapshots compared before and after (G8). |
| T-04-06-03 | Tampering | Acknowledgement matched to the wrong mutation | high | mitigate | Settlement verifies both mutation identity and fingerprint before applying any state; a mismatch refuses and mutates nothing. |
| T-04-06-04 | Information Disclosure | Store file readable before first unlock | high | mitigate | `.completeUntilFirstUserAuthentication` asserted, `.complete` explicitly excluded; the device-only half of the proof is disclosed rather than claimed (ASVS V8). |
