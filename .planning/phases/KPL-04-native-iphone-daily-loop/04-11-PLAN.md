<objective>
Give undo a name, a place, and no clock. On a phone the temptation is a snackbar; the phase forbids it, because the people who most need undo are exactly the people a five-second timer excludes.

Purpose: undo is the weakest analogue carried from the Mac, and it is the affordance that makes a cheap full-swipe Complete safe. This plan re-expresses the Mac's named-visible-action contract natively and keeps platform text undo from colliding with it.

Output: the persistent named undo control in the accessory and the overflow menu, compensating-action reconciliation through the server handle, and an explicit refusal path for an undo the client cannot honor.
</objective>

    - Settling an acknowledgement that carries no handle clears the current availability rather than leaving a stale one.
    - Invoking undo builds a compensating semantic command with a fresh mutation identity that carries the server-issued handle, and sends it through the same outbound path as any other command.

    - An undo whose own outcome is uncertain stays in the uncertain state and is never settled by the client.
    - The undo availability is single-level: the latest supported change only, matching the Mac contract.
    - The supported undo matrix is closed to task details, clarify and return, plan and unplan, complete and reopen, and Trash and restore; an unsupported command mints no undo availability.

  <action>
Create `UndoAvailability.swift` holding the single-level current availability derived from the last settled acknowledgement's server-issued handle, and `CompensatingCommands.swift` building the inverse semantic command for each entry in the closed supported matrix.

Undo is a compensating semantic action, never a local retraction: the server owns whether the compensation applied, so the client sends a fresh mutation identity carrying the server handle and settles on the server's answer exactly as it does for any other command.

Reproduce the Phase 3 decisions rather than re-deciding them. Undo of a mutation the server never acknowledged is refused at the point of action with authored copy — deferring it would require a second durability mechanism the phase does not have. An undo whose outcome is uncertain is never settled by the client, because the server itself does not know whether the compensation applied; it stays loud.

Retain undo availability on settlement in `GRDBLocalStore.acknowledge` — Plan 04-06 already established that the successful path retains it; this task consumes it and adds the clearing rule for an acknowledgement that carries none.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Server-issued undo handle -> compensating command | The handle is the server's authority to compensate; a client-minted equivalent would be an unauthorized inverse mutation. |
| Platform text undo -> semantic command surface | A collision would let a text-field gesture silently issue a task mutation. |
| Undo affordance -> the person's confidence in a cheap gesture | Full-swipe Complete is only safe because undo is reliably reachable. |

| T-04-11-01 | Elevation of Privilege | Client-minted undo without a server handle | high | mitigate | Compensating commands carry the server-issued handle; a source scan asserts no local-retraction path exists. |
| T-04-11-02 | Repudiation | An undo that appears to succeed but does nothing | high | mitigate | An unacknowledged mutation's undo is refused at the point of action with authored copy and zero store mutations; the recorded prohibition forbids a silent no-op. |
