## Why this plan exists

Plan 04-16 left the device lane reporting BLOCKED, and its stated reason was that
the phone cannot reach a Mac-hosted proxy because the lane's certificate is
self-signed. That reason is true but it is not the whole gap, and the framing
sent this plan's research in the wrong direction until it was measured.

The measured position is:

1. The four server-driven scenarios ARE proven today -- by a Node `fetch` client
   written thirty lines above the assertions in `verify-real-stack-ios.mjs`. Not
   one byte of `KeeplingSyncAdapter`, `SyncReducer`, or the GRDB outbox
   participates. That file is scrupulously honest about the DEVICE and silent
   about the CLIENT, and because it is named a real-stack lane the silence reads
   as coverage.
2. The only Swift code that has ever spoken to a live Phoenix is
   `SyncPassTests.testRealStackSettlesAPushedCapture` -- one opt-in happy path
   asserting `settled == 1`. No 401, no 409, no replay, no fence.
3. So the gap is TWO nested gaps, and the outer one is bigger, cheaper, and not
   blocked by anything: the Swift client has never met a real server's refusals
   on ANY destination, simulator included.

This plan closes the outer gap first, on the simulator over loopback, where the
production guard already permits `127.0.0.1` and no certificate question arises.
That work is permanent per-commit regression coverage and none of it is
throwaway. It then extends the SAME test class and the SAME proxy to the phone.

## Why the tailnet, and not a pinned self-signed certificate

The obvious design -- inject a `ClientTransport` whose `URLSession` delegate
pins the lane's self-signed certificate -- was researched and rejected on
evidence, not taste:

- Apple TN3179 states that making an outgoing TCP connection to a local network
  address REQUIRES the local-network privilege, that the check is implemented
  "deep in the networking stack, and thus applies to all networking APIs", and
  that device managers CANNOT configure it by MDM. The privilege resets when the
  app is deleted. So the LAN-IP route contains an irreducible human tap, which
  is the recurring manual step this project exists to remove. Apple DTS's own
  recommendation for this exact XCUITest problem is to use a server that is not
  on the local network.
- TN3179 defines a local network as one on a broadcast-capable interface. A VPN
  interface is excluded by name. A tailnet address therefore never engages the
  privilege, on any device, after any reinstall.
- `tailscale cert` issues a real publicly-trusted certificate, so the phone
  validates it with the production trust path. That deletes the entire trust
  question: no delegate, no pinning, no ephemeral certificate generation, no
  lane-only build configuration, no compiled-bytes marker scan, and no permanent
  CWE-295 finding for every mobile scanner that ever looks at this app.
- It was also MEASURED that project-level `SWIFT_ACTIVE_COMPILATION_CONDITIONS`
  does not reach SwiftPM package targets. `KeeplingSyncAdapter` is in the
  `KeeplingCore` package, so a compile-gated trust path there would have taken
  the false branch SILENTLY rather than failing the build.

A public tunnel (ngrok, Cloudflare) would also work and needs no phone setup,
but it terminates TLS at a third party and puts the fault-injection endpoint on
the open internet. Rejected for a repository that has just had its PII purged.

## The pre-existing D-21 hole this plan must not step around

MEASURED, twice, independently: `tooling/ios-lanes/device.mjs` passes no
`-configuration`, so its `xcodebuild test` takes the scheme's `TestAction`
configuration, which is **Debug**. `tooling/build-ios-signed.mjs` uses
`xcodebuild archive`, which takes `ArchiveAction`, which is **Release**.

The lane's own comment at `device.mjs:151` records that `xcodebuild test`
rebuilds and reinstalls the app, and injects `KEEPLING_BUILD_DIGEST=${digest}`
so the reinstall carries the same digest. Because `keeplingBuildDigest` is a
digest of SOURCE CONTENT and not of bytes, the two configurations produce the
identical value BY CONSTRUCTION.

So: `attestation.mjs --expect-installed` attests a Release archive, that archive
is then replaced by a Debug rebuild, and D-21 -- whose entire purpose is to
refuse a run against a different build -- cannot see it. The attested bytes are
not the tested bytes. Every `#if DEBUG` seam 04-14 walled off was live in the
binary that produced the passing device evidence.

This is squarely the class of thing the anti-vacuity contract exists to catch,
it is independent of the transport question, and Task 5 closes it.
