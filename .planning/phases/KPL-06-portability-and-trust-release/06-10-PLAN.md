<objective>
**User story:** As someone downloading Keepling to self-host, I want the Mac application to open
normally and to be able to check where it came from, so that installing it does not require me to
override a warning that is indistinguishable from malware.

Today the packaged application is unsigned. On current macOS the Control-click bypass is gone, so a
downloaded build reports itself as damaged — the highest user-visible cost anywhere in this phase,
and the marginal money cost of fixing it is zero because the paid Apple membership is already active
for the iOS signing path.

Purpose: make the distributed artifact openable, attributable and inventoried, without ever shipping
bytes different from the ones every gate tested.
Output: signing inside the packaging step, a stapled artifact gated on its code directory hash, a
SLSA Build Level 2 provenance attestation, a keyless image signature, a source-generated bill of
materials with its gap declared, and an honest public write-up.
</objective>

<task type="checkpoint:decision">
  <name>Task 1: Confirm the signing-and-digest ordering before any signing step is added</name>
  <files>(no files — this task is a decision gate; the dependent task writes the files)</files>
  <decision>
    Confirm the exact ordering of packaging, signing, digesting, notarizing and stapling, and confirm
    which identity the shipped artifact is gated on, before any signing configuration is written.

    **Why this is a one-way door.** Getting the order wrong ships a different file than the one every
    gate tested, with every gate green. The packaging script computes the application digest by
    hashing the application directory immediately after the packager step returns, and every macOS
    evidence row in this project binds to that digest. If signing is bolted on as a later step, the
    recorded digest describes bytes that no longer exist, and the failure is silent — the manifest
    says signed, the evidence says tested, and neither describes the shipped file.

    **The proposed ordering, per D-16 and D-17 (and note D-18: iOS distribution stays development-signed; TestFlight and App Store remain deferred and are not in this plan's scope):**
    1. The packager step runs with signing configured through the packager's own signing option, so
       the bundle is signed before the packaging script's hashing call executes.
    2. The application digest is computed over the signed bundle.
    3. The lossless archive is made from the signed bundle and its archive digest recorded.
    4. Notarization is submitted against the archive.
    5. The notarization ticket is stapled onto the bundle, which mutates it again, irreducibly.
    6. The code directory hash is read from the signed bundle and recorded separately — it is the
       identity that survives stapling.
    7. The manifest records both: the pre-staple application digest, which is what every gate tested,
       and the code directory hash, which is what a launch-time check on the shipped file will show.
    8. The shipped stapled artifact is gated on its code directory hash equalling the tested one.

    **The three rules that follow, and why each exists.** Do not attempt to make the directory hash
    stable across stapling — stapling mutates the bundle by design, and chasing that stability ends in
    a loosened binding. Never re-package after notarizing. Never sign recursively with the deep
    option; use per-helper entitlements through the packager's per-file callback instead, because the
    recursive option applies one entitlement set to nested helpers that need different ones.

    **The alternative that was rejected, and why.** Loosening the digest binding so it tolerates
    signing would remove the exact control that already caught a real artifact-transport defect. That
    ruling has been made once before in this project and is not being re-litigated; it is restated
    here only so the person confirming knows what is being protected.
  </decision>
  <context>
    Nothing has been signed yet. Once a release is published under a given ordering, the evidence rows
    bound to it are what the release claim rests on. Confirm at this point that the five Apple
    credentials and the attestation permission named in this plan's `user_setup` are in place, since
    the signing and notarization steps cannot execute without them.
  </context>
  <options>
    - **Confirm the ordering as proposed (recommended).** Sign inside the packager step, digest after,
      archive, notarize, staple, record the code directory hash, gate the shipped artifact on it.
    - **Change which identity the shipped artifact is gated on.** State the alternative and what it
      binds to; anything that gates on a digest recomputed after stapling is the trap this checkpoint
      exists to prevent.
    - **Defer signing entirely.** State the consequence plainly: downloaded builds continue to report
      themselves as damaged, and this becomes a disclosed limitation with a named owner and a named
      closing command rather than a silent omission.
  </options>
  <resume-signal>Reply with the option you choose (for example `A`), or describe the alternative you want.</resume-signal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| build machine → downloader | Signed and notarized bytes cross to an untrusted machine where launch-time checks are the only remaining control. |
| CI OIDC identity → Sigstore / attestation service | An ephemeral identity mints signatures; the scope of that grant decides who can sign in this repository's name. |
| repository secrets → forked pull requests | A forked pull request that could read the signing credentials would be able to sign arbitrary bytes as Keepling. |
| dependency ecosystem → signed release | Every control in this plan signs whatever it is given, including a compromised dependency. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-10-01 | Tampering | the digest recorded before signing | critical | mitigate | Signing runs inside the packager step so the hashing call observes the signed bundle; the code directory hash is recorded separately as the identity that survives stapling, and the stapled artifact is gated on it matching. A checkpoint gates the ordering before any signing step is written. |
| T-06-10-02 | Spoofing | signing credentials reachable from a forked pull request | critical | mitigate | The Apple credentials are repository secrets scoped so forked pull requests never receive them, and the signing jobs run on the main branch only; forked runs report an explicit not-run status rather than being omitted. |
| T-06-10-03 | Elevation of Privilege | workflow-wide OIDC grant | high | mitigate | `id-token: write` and `attestations: write` are granted at job level only; a gate fails if the grant appears in the top-level permissions block. |
| T-06-10-04 | Spoofing | signing a mutable image tag instead of an immutable digest | high | mitigate | The image is signed by digest; a signature over a tag would prove nothing about the bytes a puller receives. |
| T-06-10-05 | Tampering | a malicious dependency update reaching a signed release | high | accept | Explicitly accepted and disclosed: every control here would sign it. `docs/security/SUPPLY-CHAIN.md` names this as the realistic adversary and names the enforced provenance-review culture as what addresses it, rather than letting signing be read as coverage it does not provide. |
