  <name>Task 1: Decide the contributor agreement, and decide repository visibility</name>
  <files>(no files — this task is a decision gate; the dependent task writes the files)</files>
  <decision>
    Two coupled decisions, both taken before any contributor-facing document is written.

    **(a) Contributor agreement (D-25): a developer certificate of origin, or a contributor licence
    agreement?** The proposal is a certificate of origin enforced by a lane, and **no** licence
    agreement.

    *Why this is one-way in effect.* Whichever is chosen, you can never unilaterally relicense
    afterwards without every contributor's consent — the certificate route deliberately gives up
    that right, and the agreement route acquires it but cannot be applied retroactively to
    contributions already accepted under the other.

    *The case for the certificate.* The chosen licence already supplies the inbound copyright and
    patent grant from every contributor, so the certificate only has to carry **provenance** — which
    is the live risk for an AI-built, AI-native project, where a contributor or their coding
    assistant pastes copyleft code in. A contributor licence agreement buys the unilateral relicence
    right, which under this licence is nearly worthless: a closed hosted service, App Store
    distribution, dual-licensing your own copyright, and acquisition are all already available. Its
    historical exercise is what triggered the two best-known community forks of the last few years.

    *What to decide, concretely.* The certificate route adds a sign-off requirement, a pull-request
    template checkbox, and an enforcement mechanism — either a marketplace application requiring no
    workflow configuration, or a workflow action requiring a write permission if it comments. Either
    satisfies the requirement; the application is simpler for a solo-maintainer repository already at
    capacity on required lanes, but requires an organisation-level installation.

    **(b) Repository visibility.** Verified at planning time: this repository is **private**. Every
    document in this plan is addressed to readers who cannot currently see it, the release criterion
    requires this posture to be public, and the security channel this plan configures is meaningless
    to a researcher who cannot find the repository.

    *Why this is one-way.* Making a repository public publishes its entire commit history. Anything
    ever committed — a credential, a path, a personal detail — becomes retrievable even after a later
    deletion, and reverting to private does not recall what was cloned.

    *What to decide.* Whether the repository becomes public in this phase, and if so whether a history
    review is wanted first. If it stays private, say so explicitly and record it as a disclosed
    limitation with a named owner, because the release criterion about a public trust posture then
    cannot be satisfied and must not be quietly marked as met.
  </decision>
  <context>
    Nothing contributor-facing is written yet. Answer (a) decides what `CONTRIBUTING.md` and the pull
    request template say and what enforcement is wired. Answer (b) decides whether the release
    criterion about a public posture can be claimed at all, or whether it becomes a disclosed
    limitation with an owner.
  </context>
  <options>
    - **Certificate of origin, enforced by a marketplace application; repository becomes public after
      a history review (recommended).**
    - **Certificate of origin, enforced by a pinned workflow action.** Avoids an organisation-level
      installation at the cost of one more required lane and a write permission.
    - **Repository stays private for now.** State it; the public-posture criterion becomes a disclosed
      limitation with a named owner and a named closing action, never a silent pass.
  </options>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| security researcher → maintainer | The reporting channel and its stated terms are the only contract between a finder and the project. |
| published claim → reader's reliance | A self-hoster or researcher acts on what these documents say; an unenforced claim is a misstatement they relied on. |
| internal ledger → public limitations list | A divergence between the two is how a known defect disappears from public view while staying open internally. |
| repository visibility → published history | Making the repository public publishes everything ever committed, irreversibly. |
