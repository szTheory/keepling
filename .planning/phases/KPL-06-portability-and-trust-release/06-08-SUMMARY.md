# Phase KPL-06 Plan 08: Independent export verification -- completeness, no-secrets, reader, golden vector Summary

**Built D-07's four-part proof that Keepling's export claim is checkable by someone who doesn't trust the producer: a schema-driven completeness lane bound to the live database schema, a no-secrets assertion over a credential-bearing fixture, a standalone zero-shared-code Node reader that validates a bundle end-to-end and fails in six required directions, and a multi-consumer golden vector pinning the bundle's exact bytes -- deliberately with no importer.**

## Performance

- **Duration:** ~110 min
- **Tasks:** 3 (all `type="auto"`, Task 1 `tdd="true"`)
- **Files modified:** 10 (2 created, 8 modified)

## Accomplishments

- **Task 1 (completeness + no-secrets):** Extended `export_test.exs` with three completeness cases (live-schema-vs-manifest diff, a negative fixture proving the diff actually detects a removed column, and an "in classified column also present in its exported entity schema" check) and one no-secrets case that inserts session, account-recovery, and device-grant rows carrying real credential material, exports the account, and asserts none of that material -- plaintext or hashed -- appears anywhere in the bundle's raw bytes, plus that access-inventory records omit every excluded column by name. The completeness test immediately found that `classification.json` had drifted against migrations already landed earlier in this phase; closed the gap by classifying the newly-found columns.
- **Task 2 (independent reader):** `tooling/verify-export-reader.mjs` -- a standalone Node lane importing nothing from the Elixir source tree, shelling only to the system `unzip` binary, with a small hand-rolled JSON Schema validator covering exactly the eight checked-in entity schemas' vocabulary. Verified end-to-end against all six required failure directions plus BLOCKED-on-missing-bundle and zero-entity-files. Found and fixed the CLI wiring gap disclosed by 06-04 (`mix keepling.ops export` was structurally unreachable) since this task's own `<verify>` block required a real CLI-produced bundle.
- **Task 3 (golden vector):** `packages/contracts/vectors/export-golden.json` -- generated from a fixed fixture fed directly to `Export.write_bundle/4` (never a live database read), registered in `manifest.json` with both `elixir` and `tooling` consumers. `export_test.exs` gained a byte-comparison case; the reader gained a `--golden` mode that independently recomputes every recorded digest/row-count from the vector's own checked-in content. Registered both `export-elixir` and `export-reader` in `tooling/release-lanes.json`.

## Decisions Made

See `key-decisions` in frontmatter. In prose: the completeness check's own first run found a real, previously-invisible classification drift and closed it; the reader deliberately shells to system `unzip` and hand-rolls a narrow schema validator rather than adding any dependency; the golden vector is authored via a direct `write_bundle/4` call (never a live DB read) specifically to remove `restore_epoch`/`feed_high_water_sequence` as sources of environmental variance; the tooling reader's vector-conformance proof is an independent digest recomputation rather than a live bundle regeneration; and the CLI wiring gap disclosed by 06-04 was closed for the `export` verb only, since this task's own verification required it, without touching the identical gap for `backup`/`restore`/`deploy`/`upgrade`/`replace-host`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1/2 - Stale checked-in classification] classification.json was missing five real, already-landed schema changes**
- **Found during:** Task 1, first run of the new completeness test
- **Issue:** `device_grants.last_used_at` (06-07), `task_activities.actor_principal`/`actor_label`/`recovery_state`/`undone_activity_id`, and the `schema_migrations` table itself were present in the live schema but absent from `classification.json`, which the completeness test's own design makes a hard failure.
- **Fix:** Classified all five as `out` with a reason each (internal bookkeeping, or provenance detail not wired into any exported entity schema this plan).
- **Files modified:** `packages/contracts/schemas/export/classification.json`
- **Verification:** `mix test test/keepling/application/export_test.exs --only completeness` passes (3/3).
- **Committed in:** `19d12f6` (Task 1 commit)

**2. [Rule 3 - Blocking] `mix keepling.ops export` was structurally unreachable, blocking Task 2's own `<verify>` command**
- **Found during:** Task 2, attempting to run the plan's literal CLI verify command
- **Issue:** `Keepling.Release`'s `@switches`/`@operation_switches` had no entry for `export`'s `--destination-dir` input, so `OptionParser` rejected the flag before the operation ever ran; and `Keepling.Adapters.Postgres.OpsStore.execute/3` (the sole port `Release.invoke/1` ever passes) unconditionally returned `{:error, :operation_adapter_unavailable}` for every operation, mirroring the same disclosed gap 06-04 left for `backup`/`restore`/`deploy`/`upgrade`/`replace-host`.
- **Fix:** Added `"export" => ~w(destination_dir)a` to `@operation_switches` and `destination_dir: :string` to `@switches` in `release.ex`; added an `execute("export", input, options)` delegation clause in `ops_store.ex` routing to `Keepling.Adapters.Postgres.Export.execute/3`, leaving the catch-all (and therefore every other verb's disclosed gap) unchanged.
- **Files modified:** `apps/server/lib/keepling/release.ex`, `apps/server/lib/keepling/adapters/postgres/ops_store.ex`
- **Verification:** `MIX_ENV=test mix keepling.ops export --destination-dir <dir>` produces a real, valid bundle; full `mix test` suite (337 tests) passes with no regression.
- **Committed in:** `553e873` (Task 2 commit)

**3. [Rule 3 - Blocking] `tooling/check-contracts.mjs` hardcoded "expected 15 vector files"**
- **Found during:** Task 3, running `pnpm contracts:check` after registering the 16th vector file
- **Issue:** The cross-consumer gate's file-count assertion was a literal `15`, which would reject `export-golden.json`'s addition outright regardless of correct registration.
- **Fix:** Bumped the literal to `16` and generalized the adjacent docstring (which already said a stale `13`).
- **Files modified:** `tooling/check-contracts.mjs`
- **Verification:** `pnpm contracts:check` passes: "Vector manifest gate passed: 16 vector files, 20 consumer entries proven executed."
- **Committed in:** `56638e5` (Task 3 commit)

## Issues Encountered

- **`tooling/release-lanes.json`'s two new lanes are registered but not yet individually reported by a live CI job.** `export-elixir`'s `job` field names `phase2-linux` (where the full `server` Phase 2 lane, including `export_test.exs`, already runs) and `export-reader`'s names `ci-contract` (where `pnpm contracts:check` already runs) as the lanes' eventual homes, but neither CI job currently emits a release-manifest entry naming these two lanes individually -- `.github/workflows/repository-integrity.yml` was not in this plan's declared `files_modified`. As a direct, expected consequence, running `node tooling/verify-release.mjs --manifest .planning/releases/candidate-0/release-manifest.json --offline` (the plan's own overall `<verification>` command) now fails with two `lane vanished from manifest` errors, since candidate-0's committed manifest predates these lanes. **This is the intended proof that the exact-set detection works** -- exactly what the plan's success criteria describe ("their disappearance from a release manifest is a hard failure rather than a pass") -- not a defect introduced by this plan. Wiring a real CI job to emit `export-elixir`/`export-reader` entries into a fresh release manifest (mirroring how `ci-contract`'s own job already does this for itself) is disclosed as open work for a future plan or CI-focused amendment.
- **The literal CLI verify command in the plan text (`mix keepling.ops export --output <path>`) did not match the real application input contract.** `Keepling.Application.Export.write_bundle/4` and `Keepling.Adapters.Postgres.Export.execute/3` take a `destination_dir` (a directory the writer creates `<account_id>-export.zip` inside), not an exact output file path. Task 2 was executed and verified using the real flag (`--destination-dir <dir>`) and by locating the resulting `<account_id>-export.zip` inside that directory, rather than the plan's illustrative (and non-matching) `--output` flag.
