<objective>
**User story:** As Keepling's maintainer, I want one command that proves a named revision's
artifacts and evidence lanes are the ones actually tested, so that I can make a release claim a
third party can check instead of a claim only I can vouch for.

This plan carries the **phase tracer**. Task 1 is a `type="tracer"` slice: it wires one lane and one
artifact through every layer the release-evidence spine will ever touch — CI job → artifact digest →
`release-manifest.json` → `verify-release.mjs` → committed retention under `.planning/releases/` —
and proves that single path end-to-end before any expansion. Tasks 2 and 3 expand outward from the
proven slice: Task 2 makes the rest of CI actually able to run, Task 3 makes the artifact transport
lossless so real digests survive it.

Purpose: without this spine, D-09's authority model and every later plan's evidence claim are
incoherent — nothing can bind evidence to a revision.
Output: `tooling/verify-release.mjs`, `tooling/release-lanes.json`, a first committed manifest, a
CI pipeline whose lanes can actually execute, and a lossless artifact transport.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CI runner → artifact store → consuming job | Built bytes cross an untrusted transport; a mode-losing transport silently changes the identity of the tested artifact. |
| committed `release-manifest.json` → third-party verifier | An external reader trusts the manifest as the statement of what was tested; it must be checkable without trusting the producer. |
| branch protection → merge authority | GitHub's required-check evaluation decides what may reach `main`; a skipped check is indistinguishable from a passing one. |
| GitHub attestation service → offline verifier | Network availability must not decide whether the release claim can be stated. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-02-01 | Tampering | artifact transport between `desktop-package` and `desktop-packaged` | high | mitigate | `ditto -c -k --sequesterRsrc --keepParent` out, `ditto -x -k` in, `archiveDigestSha256` recorded, and the expanded tree re-hashed against `applicationDigestSha256` — the binding stays, the pipe is fixed. |
| T-06-02-02 | Spoofing | `release-manifest.json` lane records | high | mitigate | `verify-release.mjs` asserts each PASSED lane's `ranAgainstArtifactDigest` exists in `artifacts[]` and that `cases` is positive, so a lane cannot claim to have tested bytes that are not in the manifest. |
| T-06-02-03 | Elevation of Privilege | branch protection required checks | high | mitigate | Single `all-required-passed` aggregator with `if: always()` asserting every `needs.*.result == 'success'`; `if:` banned on required jobs by `check-ci-contract.mjs`; no admin bypass. |
| T-06-02-04 | Repudiation | vanished lane in a manifest | high | mitigate | `tooling/release-lanes.json` is a committed closed inventory and a missing lane exits non-zero, proven by the `release-manifest.vanished-lane.json` fixture. |
| T-06-02-05 | Denial of Service | GitHub attestation endpoint unavailable | medium | accept | Verification degrades to `attestation=UNVERIFIED` printed loudly and continues; the provenance half is lost, the claim remains statable. Accepted because the alternative — hard-failing on an outage — makes an external service a release blocker. |
| T-06-02-06 | Information Disclosure | `release-manifest.json` committed to git | low | accept | The manifest carries digests, run ids, job names and runner images only; no credentials, no user content. Accepted. |
| T-06-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new package-manager dependency lands in this plan; `ditto`, `grep` and `asdf` are runner-native. RESEARCH.md's Package Legitimacy Audit records no `[SUS]` or `[SLOP]` package, so no legitimacy checkpoint is required here. |
