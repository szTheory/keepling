<objective>
**User story:** As a Keepling user holding an export bundle, I want to be able to check for myself
that it is complete and readable without Keepling, so that "you can take your data out" is something
I can verify rather than something I have to believe.

Plan 06-04 built the producing half. This plan is D-07's four-part proof: schema-driven completeness so
a migration cannot silently omit a field; a golden vector so the bytes are pinned; an independent
reader sharing zero Elixir code so inspectability is demonstrated rather than asserted; and a
no-secrets assertion. There is deliberately **no importer** — an importer is a permanent second
compatibility surface with real attack surface, and it proves only self-consistency, which is
exactly the failure mode of formats only the product can read.

Purpose: make the portability claim checkable by someone who does not trust the producer.
Output: an independent reader, a registered golden vector, and a completeness check bound to the
live schema.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| producer (Elixir) → verifier (Node) | The independent reader exists precisely because a verifier sharing the producer's code proves only self-consistency. |
| database schema → export classification | A migration changes the schema without touching the export; the classification manifest is the only thing that notices. |
| export bundle → any reader | The bundle is handed to programs and people outside the product's control. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-08-01 | Information Disclosure | credential material serialized into the bundle | high | mitigate | A no-secrets assertion greps the produced bundle's raw bytes for fixture credential values, run from both the Elixir lane and the independent reader, so an accidental serialization into an unexpected field is caught by two independent routes. |
| T-06-08-02 | Tampering | a future migration silently omitting a field from every export | high | mitigate | The completeness case diffs the live `information_schema.columns` against the checked-in classification manifest and fails naming the table and column; the failure direction is proven by a negative fixture rather than assumed. |
| T-06-08-03 | Spoofing | a partial bundle presented as a complete history | high | mitigate | Per-file digests and row counts in a manifest written last; the independent reader fails on digest mismatch, row-count mismatch, malformed line, or zero entity files. |
| T-06-08-04 | Repudiation | an export lane vanishing from a release manifest | medium | mitigate | Both lanes are registered in `tooling/release-lanes.json`, which `verify-release.mjs` compares as an exact set, so a vanished lane is a hard failure. |
