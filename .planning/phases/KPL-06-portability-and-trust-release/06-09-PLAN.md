<objective>
**User story:** As a Keepling user whose Mac and server disagreed, I want to see exactly which
fields diverged and choose per field, so that resolving a conflict does not cost me the fields I
never disagreed about.

Two coupled defects close here. The conflict resolver renders exactly one field with two
whole-conflict choices, so a lifecycle or Trash disagreement has nowhere to appear — which is why a
durable refusal record alone would not be a fix. And the desktop keyboard commands call the route
setter directly, walking straight past the dirty-state guard that the mouse path already honours.

Purpose: make the durable refusal record from plan 06-06 actionable, and stop a keystroke from
discarding unsaved work.
Output: a per-field, lifecycle-aware resolver; recovery-strip surfacing for unattended refusals; and
keyboard navigation that goes through the guard.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| keyboard input → navigation → unsaved editor state | A keystroke can destroy authored work that has not reached storage; this is the loss window the durable refusal record cannot see. |
| durable refusal record → rendered resolver | If the resolver cannot render a divergence class, the person cannot act on the record and the data-loss fix is incomplete. |
| staged per-field choices → submitted mutation set | Fields outside the conflicting set must not be carried into the mutation. |
