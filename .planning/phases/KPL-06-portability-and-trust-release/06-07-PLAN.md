<objective>
**User story:** As a Keepling user reviewing my authorized agents, I want the consent screen to tell
me what each agent may actually do and when it was authorized, so that revoking is an informed
decision instead of a guess.

A phase named "Trust Release" cannot ship a consent screen that renders a placeholder for what an
agent may do. This plan publishes the real values, closes the receipt-scope inversion that lets any
write-scoped holder read another grant's mutation receipt, and preserves the absent-versus-empty
distinction that a prior UI review already had to establish once.

Purpose: the consent surface is the product's only honest account of delegated authority.
Output: real published grant fields, a receipt read bound to its issuing grant, and a UI that states
unknown and zero as different things.
</objective>

  <files>(no files — this task is a decision gate; the dependent task writes the files)</files>
  <decision>
    Decide which event(s) should advance `last_used_at` for a device grant, before the migration and
    the write path are written.

    **Why this is being asked rather than assumed.** RESEARCH.md verified against source that there
    is no `last_used_at` column on `device_grants` and no code path anywhere in
    `apps/server/lib/keepling/accounts/` or `apps/server/lib/keepling_web/` that writes a last-used
    timestamp — a grep for `last_used` returns zero hits. `authorized_at` maps cleanly to the existing
    `inserted_at` with no schema change. `last_used_at` cannot reuse `last_refreshed_at`: that column
    advances only on OAuth refresh-token rotation, so publishing it under a last-used label would
    narrow the claim to "last token refresh" while the screen says something broader.

    **Why it is a one-way door.** The answer becomes a published contract field on
    `DeviceGrantSummary` and a sentence the consent screen asserts to the user about their agents.
    Changing the semantics later changes the meaning of timestamps already shown and already stored,
    with no way to recompute history that was never recorded.

    **The options and their consequences:**

    - **Every authenticated request.** Most faithful to the words "last used". Highest write volume —
      a write per request on a hot path, needing debouncing or a coarsened granularity to avoid row
      contention on a small single-host VM. Coarsening is itself a privacy choice: a one-minute
      granularity says less about the person's activity pattern than a per-request timestamp.
    - **Only mutations.** Far lower write volume and arguably the more meaningful signal for a
      consent screen — it answers "when did this agent last change something of mine". But an agent
      that reads all of someone's tasks every hour and never writes would show as never used, which
      on a consent screen is misleading in the dangerous direction.
    - **Only MCP tool calls.** Narrowest, and closest to D-38's animating concern, which is the
      agent-consent screen specifically rather than device-grant activity in general. But the same
      field is published for the Electron and iPhone grants, where it would then always be null, and
      a field that means different things per client kind is exactly the kind of collapse this
      surface exists to avoid.

    **What to decide:** which event advances the column; what granularity is stored; and whether a
    null value after the write path exists means "never used" or still means "not measured for this
    client kind". The last sub-question is load-bearing for the UI, because 06-UI-SPEC.md reserves
    two distinct copy strings for those two states and forbids collapsing them.
  </decision>
  <context>
    Nothing is written yet, so this is the cheap moment. The answer determines the migration's
    column, whether a companion write lands on a hot authentication path or only in the MCP tool-call
    path, and which of the two reserved copy strings the UI may render for a null value.
  </context>
  <options>
    - **Only mutations, with a null meaning not-measured (a defensible default).** Low write volume,
      meaningful signal, and the UI keeps rendering the not-yet-reported copy for a null.
    - **Every authenticated request at a coarsened granularity.** Most faithful to the label; state
      the granularity, because it is a privacy decision as well as a performance one.
    - **Only MCP tool calls.** Narrowest; if chosen, state explicitly what the field means for the
      Electron and iPhone grants so the screen does not publish one label for two meanings.
  </options>
  <resume-signal>Reply with the option you choose (for example `A`), or describe the alternative you want.</resume-signal>
  <done>The advancing event, the stored granularity, and the meaning of a null value are decided and recorded in the plan summary before Task 2 begins.</done>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent bearer token → mutation receipt read | An agent-authenticated request reads a stored mutation result; the authority check decides whose results it may see. |
| server grant record → consent screen | The screen is the user's only account of delegated authority; an inaccurate field is a security misstatement, not a cosmetic bug. |
| authentication hot path → bookkeeping write | A last-used write on an authenticated path is a new write on a request path. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-07-01 | Elevation of Privilege | `agent_authority/2`'s receipt clause and `Commands.lookup_result/3` | high | mitigate | The lookup is bound to the issuing grant, so a leaked mutation id grants no cross-grant read; proven by a test with two distinct grants holding the same scope. Non-enumerable identifiers are treated as a coincidence, not a control. |
| T-06-07-02 | Information Disclosure | the constant 403 body | medium | mitigate | The refusal body stays byte-identical and names neither the missing scope nor whether the mutation exists, so the refusal itself leaks no existence signal. |
| T-06-07-03 | Spoofing | a consent screen asserting an unmeasured last-used fact | high | mitigate | A null last-used value maps to the unknown copy; the zero-activity copy is reachable only once the server can prove zero recorded activity. The gate counts occurrences of the unknown copy to catch a collapsed branch. |
| T-06-07-04 | Information Disclosure | publishing grant scope over the wire | low | accept | The scopes are the user's own delegated authority shown to the authenticated account owner; no credential material is added to the response. Accepted. |
