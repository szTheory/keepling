<objective>
Make under-determination a refusal rather than a guess. The failure mode this requirement exists to
prevent is a language model silently editing the wrong task, so the plan is structural: writes are
addressed by opaque identity only, disambiguation is a separate read that mutates nothing, and the
three outcomes — resolved, none, too many — are three distinct closed errors.

The same structure carries the phase's central security property. Task content is untrusted data;
authorization outcomes must be incapable of depending on it. That is not a filter applied to text,
it is the absence of any code path that hands text to an authorization decision.

Purpose: MCP-03 in full, plus D-24, which is the security property the whole phase exists to
establish.

Output: one identity-only resolution function, a bounded candidate response, and a test that proves
free text never reaches an authorization decision.
</objective>

<task type="checkpoint:decision">
  <name>Task 1: Confirm identity-only write addressing and content-independent authorization</name>
  <decision>
Two one-way doors, and they are the two the phase exists to establish.

**(a) D-15 — writes address tasks by stable opaque identity only.** A title, a description, or any
natural-language phrase is never a write address. An agent that only has a phrase must first call a
read (search or the candidate lookup), then issue the write against an identity it received.
- Option A (recommended, CONTEXT-locked): identity-only, as described. This is Phase 1 D-18
  applied to the surface where the caller is a language model.
- Option B: accept a phrase as a write address when it resolves uniquely.
Cost of undoing later: name-addressed writes, once published, are what hosts build against;
withdrawing them breaks every integration that adopted them. And Option B's "resolves uniquely"
is a property of the data at one instant, not of the request.

**(b) D-24 — authorization never depends on content.** Scope checks, preview binding, and candidate
resolution read structural fields only. No path exists by which text stored in a task can widen a
grant, mint or alter a preview token, or cause a commit.
- Option A (recommended, CONTEXT-locked): enforce this by construction — the authorization
  functions do not take text as an argument at all — and prove it with the test in task 3.
- Option B: allow content into these paths and filter it.
Cost of undoing later: this is the security property the phase exists to establish. A
content-influenced authorization path found later invalidates every claim the phase makes,
including the evidence lanes' verdicts.
  </decision>
  <context>
`05-CONTEXT.md` records Option A for both. `05-CONTEXT.md` § Specific Ideas states the threat model
plainly: the interesting attack is a task whose notes tell the model to escalate, not an
unauthenticated request. `packages/contracts/vectors/redaction.json` already carries a
`hostile_sentinels` list that is the right shape for the corpus plan 05-11 builds on top of this.

Confirming Option A for both is expected. The record of having confirmed it is what a later
security audit reads.
  </context>

fields only.

member from 05-05's vocabulary, with the candidate list in a structured `data` field, each
candidate projected through `MCP.Redaction`. The human string stays a fixed literal; the candidate
list is structured data beside it, never interpolated into it.

Route every write tool in `KeeplingWeb.MCP.Tools` through `TaskAddressing.resolve/3`. No write tool
performs its own lookup, and none accepts an addressing key the resolver does not.

| T-05-28 | Elevation of Privilege | scope gate, preview binding, candidate selection | critical | mitigate | The functions take structural arguments only; `content_isolation_test.exs` asserts the call-site key sets and runs a sentinel-versus-empty differential proving identical outcomes |
