<objective>
Close the agent privilege escalation that phase verification found by probe, and settle the
grant-administration authorization question it is entangled with.

`KeeplingWeb.MCP.Pipeline` refuses a grant whose `client_kind` is not `mcp`. Nothing performs the
mirror-image refusal, so an MCP agent credential passes `authenticate_device_grant/1` and reaches
`/api/v1/sync`, `/api/v1/sync/bootstrap`, and both `/api/v1/device-grants` routes. Probed with a
grant scoped `tasks.read` alone, it read the whole account around the bounded, paginated, redacted
surface that 05-03 and 05-04 built, and revoked another installation — in production, an agent
switching off the owner's iPhone.

Two things make this more than a missing guard. The evidence harness depends on the hole:
`tooling/mcp-client/final-state.mjs` reads the grant list with a device-grant bearer and asserts
`200`, so the green `simulated-client` lane rests on the escalation it should be catching. And
every lane in this phase tests for under-delivery — an agent denied something it should have —
while none tests over-delivery, which is the blind spot this lived in.

Purpose: MCP-01 and the phase goal's "recovery model" clause are both false until this closes.

Output: symmetric pipelines, an owner-session route for grant administration, adversarial cases
that fail if either regresses.
</objective>

## Task 1 — Make the two pipelines symmetric

`KeeplingWeb.Auth.authenticate_device_grant/1` (auth.ex:117-149) already derives `client_kind` from
the grant and assigns it. Refuse `mcp` there, mirroring `mcp/pipeline.ex:34`, with the same problem
shape the surrounding code uses.

Decide deliberately whether the refusal belongs in the pipeline or per-route, and say which in the
SUMMARY. The pipeline fronts `/api/v1/sync`, `/api/v1/sync/bootstrap`, and both
`/api/v1/device-grants` routes (router.ex:120-127); all four are first-party-client surfaces and an
agent should reach none of them.

Add server tests: for each of the four routes, an `mcp`-kind grant is refused, and an `iphone`- or
`electron`-kind grant still succeeds. The second half matters — a refusal that also breaks the real
clients is not a fix.

## Task 2 — Give grant administration an owner-session route

The owner's browser cannot manage agent grants today: `apps/web/src/api/keepling.ts:600` calls
`/api/v1/device-grants` with cookies, while
`apps/server/test/keepling_web/device_grant_controller_test.exs` deliberately asserts that route
401s a browser cookie. Two plans in one phase encoding opposite intentions for one endpoint.

Resolve it WITHOUT weakening either: leave `/api/v1/device-grants` bearer-only with its assertions
intact, and add a separate owner-session route for grant administration behind `:authenticated`,
with `:mutation` on the delete. Re-point the web client at the new route.

If you conclude a different shape is better, you may take it — but you may not move the existing
routes to `:client_authenticated`, and you must state the reasoning in the SUMMARY.

## Task 3 — Re-point the harness off the hole

`tooling/mcp-client/final-state.mjs:68-78` reads the grant list with a device-grant bearer. Once
Task 1 lands, that call is refused and the `simulated-client` lane breaks — correctly. Re-point it
at the owner session, the same way the e2e spec establishes one.

The lane must still prove what it proved before. If its evidence genuinely weakens, say so in the
SUMMARY rather than quietly narrowing the assertion.

## Task 4 — Test over-delivery, not just under-delivery

Add adversarial cases that aim an agent credential at each of the four routes and require refusal.
These belong in `tooling/mcp-lanes/adversarial.mjs` so the gate fails if any route regresses.

Then re-run the full gate (`KEEPLING_E2E_POSTGRES_PORT=55442 pnpm run verify:mcp:phase`) and the
phase-1 suite (`KEEPLING_E2E_POSTGRES_PORT=55442 pnpm test:phase-1`). `agent-access.spec.ts` should
now pass to completion; it currently fails at line 250. The `cross-adapter` lane stays BLOCKED on
its electron and iphone legs — that is window #69 and is NOT in scope here.

Report the lane table and the MCP-01 evidence position in the SUMMARY. Do not check any box in
`.planning/REQUIREMENTS.md`; record the evidence and leave the decision to re-verification.
