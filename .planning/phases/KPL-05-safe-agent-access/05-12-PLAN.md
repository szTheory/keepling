  <action>
Create `tooling/cross-adapter/scenario-report.mjs` defining the evidence contract every leg obeys.
Each leg, for each scenario, emits one line beginning `CROSS_ADAPTER_SCENARIO` and carrying: the
run identifier, the leg name, the scenario name, the server-returned result code, the conflict shape
identifier when the scenario produced one, the identity of the activity fact the server recorded,
and the final revision of each affected task. Every one of these values is read back from the
server's own APIs after the action, not reported from the leg's own memory of what it sent. A
client-side assertion can only report what the client believes it sent; that is exactly the class of
evidence this phase refuses.

Give the module a parser and a comparison function: parse every leg's lines, group by scenario, and
assert equality of result code, conflict shape, and activity record across every leg. A scenario
present in some legs and absent from others is a failure, not a partial pass.

Create `tooling/verify-cross-adapter-phase.mjs`. It starts exactly one real Phoenix and Postgres
instance through the shared harness, computes one `inputDigestFor` over the server source tree, and
mints one run identifier. It then runs the legs in sequence against that one instance, ranking the
slow ones first so an unavailable simulator is discovered in seconds. Every leg's evidence must
carry the same run identifier and the same input digest; a mismatch fails the run, because that is
what "one server revision" means operationally.

Copy the shortcut-refusal guards from `tooling/verify-real-stack-desktop.mjs:31-67` and add the
MCP-specific one: no leg may bypass the real authorization flow with a hand-injected bearer.

Reuse `tooling/mcp-client/scenarios.mjs` as the scenario set rather than writing a second one. A
second scenario set is a second thing that can disagree with the first.

Write `docs/testing/cross-adapter-testing.md`: how to run the lane, what each leg needs, how long
each takes, what a BLOCKED leg means, and why the lane is a phase-gate cadence rather than a
per-commit one.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Adapter leg → evidence line | Where a client's belief could be substituted for the server's record |
| Run identifier and input digest → "one server revision" claim | Where a composite of separate runs could be presented as one gate |
| Lane result → SRV-02's completion claim | The last boundary before a milestone-level claim is published |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-63 | Repudiation | leg evidence | critical | mitigate | Every value in a `CROSS_ADAPTER_SCENARIO` line is read back from the server's own APIs after the action; no leg reports its own success |
| T-05-64 | Repudiation | composite of separate runs | critical | mitigate | One run identifier and one input digest are minted once per invocation and carried through every leg; a mismatch fails the run |
| T-05-65 | Repudiation | a leg asserted from a fixture | critical | mitigate | A leg that cannot run throws a blocked-prefixed error and blocks the lane; substitution from a fixture, a cache, or another leg has no code path |
| T-05-66 | Tampering | stubbed adapter in a leg | high | mitigate | The shortcut-refusal guards from `verify-real-stack-desktop.mjs` plus the MCP-specific hand-injected-bearer guard |
| T-05-67 | Repudiation | premature SRV-02 completion | critical | mitigate | The requirement is marked only on a run where every leg ran and none blocked; the verify gate asserts the two cannot disagree, and the entry carries a citation to the run |
| T-05-68 | Denial of Service | slow legs | low | accept | The simulator boot and packaged build make this a phase-gate cadence rather than a per-commit one; documented in `docs/testing/cross-adapter-testing.md` |
| T-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package-manager install occurs in this plan; every leg reuses harnesses already in the repository. Any future install proposal requires the package-legitimacy gate and a blocking human checkpoint first |
</threat_model>
