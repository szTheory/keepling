<objective>
Prove the whole Phase 5 architecture with one production-quality end-to-end slice: an MCP host
authorizes as a first-class agent client, calls one write tool over the real Streamable HTTP
transport, and the resulting task lands in Postgres through the same `Commands.dispatch/3` the
web, Electron, and iPhone adapters use — with the agent named as the actor in the existing
activity feed.

**Phase goal (from ROADMAP, verbatim — not user-story shaped; see the planner note in the return
message):** External AI tools can use Keepling meaningfully without bypassing its authorization,
domain rules, or recovery model.

Purpose: every later plan in this phase widens this slice. If the placement (D-01), the credential
class (D-05), the two-layer scope check (D-06), or the pinned revision (D-04/D-30) is wrong, this
plan finds out after one commit rather than after ten.

Output: an agent-capable device-grant schema, a mounted MCP endpoint speaking the pinned revision,
one working write tool, and an end-to-end test that exercises all of it against real Postgres.
</objective>

<task type="checkpoint:decision">
  <name>Task 1: Confirm the three one-way authorization doors before any of them is published</name>
  <decision>
Three decisions in this plan are one-way. Once an MCP host stores a grant against them, changing
them silently changes what an existing grant permits.

**(a) D-06 — the agent scope vocabulary.** Proposed, exactly: `tasks.read`, `tasks.write`,
`tasks.bulk`. Absent scope means denied; there is no wildcard and no implicit grant. Permanently
outside any agent scope: account credentials, session and device-grant administration, recovery,
export, permanent deletion.
- Option A (recommended, CONTEXT-locked): three strings as spelled above.
- Option B: two strings — fold `tasks.bulk` into `tasks.write` as a property.
Cost of undoing later: the strings are a published authorization contract that hosts persist
inside stored grants; renaming or re-scoping them changes the meaning of grants already issued.

**(b) D-07 — credential posture.** Proposed: authorization-code plus S256 PKCE with exact redirect
binding, reusing the existing device-grant seam. No client-credentials grant. No long-lived static
API key, in this phase or any later one.
Cost of undoing later: issuing a static key puts credentials in the wild that outlive the decision
to stop issuing them.

**(c) Identity-model widening — the assumption delta, advisory.** `client_kind` has meant "one of
two human-operated devices". This plan makes it mean "human devices plus a non-human agent class",
and the activity `actor` vocabulary goes from human-only to human plus agent. Two honest answers
exist and both are fine; what is not fine is widening a CHECK constraint without asking:
- Option A (recommended): keep the `device_grants` table and the "device grant" name. The
  lifecycle — authorization code, PKCE, rotating refresh family, replay detection, per-installation
  revocation — is the thing being reused, and it is exactly right for an agent. The name is
  historical, not descriptive.
- Option B: introduce a separate `agent_grants` table and actor vocabulary. Costs a second
  authorization implementation to keep in sync, which D-02 and D-06 exist to prevent.
  </decision>
  <context>
`.planning/phases/KPL-05-safe-agent-access/05-CONTEXT.md` records Option A for all three under
