<objective>
Make the MCP authorization surface discoverable and connectable by both representative hosts
without opening it to the public internet. This closes the gap research found in D-29: Claude Code
works from a pre-registered `client_id`, Claude Desktop performs Dynamic Client Registration
unconditionally with no fallback, so settling DCR either way silently drops one host.

Purpose: plan 05-01 proved the transport and the grant. A real host cannot reach either of them
until it can discover the endpoints (RFC 9728, RFC 8414) and, for one of the two hosts, register
first (RFC 7591).

Output: two well-known discovery documents, a `WWW-Authenticate` challenge that points at them, an
audience-bound token check, and a session-gated registration endpoint.
</objective>

<task type="checkpoint:decision">
  <name>Task 1: Confirm the scoped registration endpoint before it becomes reachable by a host</name>
  <decision>
D-29 is one-way: a registration endpoint, once a host has reached it, is part of the published
authorization surface and cannot be withdrawn without breaking every host that adopted it.

The proposal: implement RFC 7591 Dynamic Client Registration at `POST /oauth/register`, gated
behind the existing authenticated browser session, so registration only succeeds for a caller who
has already proven ownership of the single Keepling account.

- Option A (recommended, CONTEXT-locked D-29): scoped DCR as described. Both representative hosts
  connect. Open registration abuse is refused by the session gate. Consistent with D-003's
  single-account exclusivity, and with the Deferred Ideas exclusion of "DCR for arbitrary
  third-party MCP hosts" — this is not that.
- Option B: pre-registration only. Simpler and smaller published surface, but Claude Desktop's
  connector flow performs DCR unconditionally with no fallback, so this host cannot connect at all.
  Choose this only if Claude Desktop is genuinely not a host you intend to dogfood with.
- Option C: unauthenticated DCR. Rejected — it is the public registration surface the Deferred
  Ideas section explicitly excludes and invites unlimited client minting.

This also settles research Open Question 2: which hosts are dogfood targets on day one.
  </decision>

loop. Note that D-29 does not weaken D-07: the grant itself is still authorization-code plus S256
PKCE with explicit scope-naming consent, and there is still no static key and no
client-credentials grant.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public internet → `/.well-known/*` | Unauthenticated reads of the discovery documents |
| MCP host → `POST /oauth/register` | Untrusted registration body, gated by the owner's browser session |
| MCP host → `/mcp/v1` bearer | Audience-bound token presentation |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-08 | Denial of Service | `POST /oauth/register` | high | mitigate | Registration requires an authenticated Keepling session and is rate-limited through the existing `hammer` bucket; unlimited unauthenticated client minting has no reachable path |
| T-05-09 | Elevation of Privilege | `KeeplingWeb.MCP.Registration` | high | mitigate | `account_id`, scope, and client kind come from `conn.assigns`; the closed-key body validator rejects any attempt to supply them |
| T-05-10 | Spoofing | `/mcp/v1` bearer check | high | mitigate | RFC 8707 audience binding — a grant issued for a different resource URI is refused and the rejection is audited (confused-deputy token reuse) |
| T-05-11 | Spoofing | registered `redirect_uris` | high | mitigate | One exact-match validation function serves both configured and registered redirects; no wildcard, no prefix match, scheme branched by client kind |
| T-05-12 | Information Disclosure | `/.well-known/*` | low | accept | The documents are required by the specification to be public and contain only endpoint URLs and the scope vocabulary; the golden key-set assertion prevents an account-specific field being added by accident |
| T-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package-manager install occurs in this plan. Any future install proposal requires the package-legitimacy gate and a blocking human checkpoint for `[ASSUMED]`/`[SUS]` packages first |
</threat_model>
