<objective>
Close the scope half of the agent authorization boundary. 05-13 closed the kind half.

A credential's authority is `client_kind` × `scope`. 05-13 made `client_kind` default-deny on
`:device_grant_authenticated`. Scope outside `/mcp/v1` is not merely unchecked — it is not carried.
`authenticate_device_grant/1` assigns `current_client_kind` and never assigns `current_scope`, so
the 19 shared `/api/v1/commands/*` endpoints could not check it if they tried, and
`CommandController` contains no reference to scope.

`Keepling.Application.AgentScope` describes itself as "the authoritative, application-boundary
scope gate" so that "a bug in the adapter alone cannot widen what an agent grant may do". Every one
of its call sites is inside `lib/keepling_web/mcp/`. The gate is adapter-local, which is the exact
property its own moduledoc denies.

Probed with real PKCE grants: a `tasks.read`-only grant POSTed `/api/v1/commands/capture-task` and
got 201 persisted, and `/api/v1/commands/trash-task` and got 200 with the owner's subsequent read
returning 404. The same token at `/mcp/v1` is refused `insufficient_scope`. The agent reaches all
19 shared commands, roughly 15 of which the MCP tool set deliberately never exposes — trash,
restore, undo, resolve-conflict, plan-for-today, move-today, and five org commands.

Purpose: MCP-02's "least-privilege scopes" clause is false until this closes.

Output: an agent credential bounded by its grant on every surface, and lane cases that fail if it
stops being.
</objective>

## Task 1 — Decide the shape, and justify it against the evidence

Two candidate fixes:

**A. Refuse `mcp` on `:client_authenticated` and `:client_mutation`.** Consistent with 05-13's
allow-list, default-deny, small. Re-verification looked for a consumer that would break and found
none: `mcp/resources.ex` and `mcp/tools.ex` call `Keepling.Application.Search` in-process and make
no HTTP calls, `final-state.mjs` uses the owner session, and the cross-adapter `web-api` leg posts
with session cookie + CSRF.

**B. Carry `current_scope` and enforce it in `CommandController`.** Larger, but keeps agents on the
shared surface under their grant's actual scopes.

Pick one and say why in the SUMMARY. If you pick A, you MUST first confirm the no-consumer finding
yourself rather than inheriting it — search for any caller that sends an `mcp`-kind bearer to
`/api/v1`, and report what you searched. If you find one, A is wrong and B is the answer.

Note `authenticate_client/2` admits EITHER credential class (D-49). Whatever you do must leave the
owner's browser session with exactly the access it has today. Do not narrow the session path.

If you choose A, delete or correct the `auth.ex:147` comment claiming that surface is
"scope-checked and bounded". Bounded is true. Scope-checked is impossible while the scope is absent
from the conn, and leaving that sentence in place is how the next reader concludes the boundary is
already covered.

## Task 2 — Prove it at the boundary

Server tests, both directions:
- A `tasks.read`-only grant is refused on `/api/v1/commands/capture-task` and `/api/v1/commands/trash-task`.
- A `tasks.write`-only grant is refused on `/api/v1/search` and `/api/v1/projects`.
- The owner's browser session still succeeds on all four.
- If you chose B: a grant WITH the right scope still succeeds, so the check is not a blanket denial.
