<objective>
Make bulk and destructive agent changes two-step and atomic. Preview returns an opaque,
account-bound, expiring token binding the exact target set, each target's expected revision, the
command and its arguments, the server instance, and the synchronization epoch. Commit accepts only
that token and a mutation identity — never a re-sent target list, which would let the committed set
differ from the previewed one.

Purpose: MCP-05 in full. Its whole content is the atomicity guarantee, and the guarantee is only
worth anything if partial success is structurally unrepresentable rather than merely avoided.

Output: `Keepling.Application.Preview`, its transactional Postgres adapter, the two MCP tools, and
a concurrent-mutation test that proves drift aborts everything.
</objective>

<task type="checkpoint:decision">
  <name>Task 1: Confirm atomic-only commits, and settle the token's storage</name>
  <decision>
**(a) D-18 — atomic commit, no partial writes. One-way.** Any drift between preview and commit —
a target changed, disappeared, or the set no longer matches — fails as `preview_stale` with zero
partial writes. Partial success is not a representable outcome of a commit.
- Option A (recommended, CONTEXT-locked): as described. Enforced by a single transaction that locks
  every target, re-reads every live revision, and writes only after all of them verify.
- Option B: best-effort commit reporting which targets succeeded.
Cost of undoing later: this is the guarantee the requirement is written to buy. A partial-write
path added later invalidates every prior claim, including every green evidence lane in this phase.

**(b) D-34 — the token's storage. Not one-way; decide it now to avoid a mid-task detour.** Research
recommends a signed opaque HMAC value mirroring the existing cursor construction, with the
counter-consideration flagged in Assumption A2 and Open Question 1.
- Option A (recommended, CONTEXT-locked D-34): signed opaque value. Mirrors an already-audited
  construction, needs no new table and no cleanup job, and replay of a committed token degrades to
  the existing idempotent-mutation-identity behaviour. Atomicity is unaffected: the check happens
  against live rows regardless of where the expected values are stored.
- Option B: a durable `pending_previews` row. Buys one thing the signed value cannot — an
  operational kill switch that invalidates all pending previews server-side. With a
  fifteen-minute-class expiry and a single account, that switch has little to act on. Choose this
  only if you want that lever.
  </decision>

  <behavior>
    - A commit over N targets whose live revisions all match the binding writes all N and returns one result carrying the new revisions.
    - A commit where one target's revision advanced between preview and commit returns `preview_stale`, and afterwards every one of the N targets is at the revision it held before the commit began — including the N-1 that would have succeeded.
    - A commit where one target was trashed or hard-deleted between preview and commit returns `preview_stale` with the same zero-write property.
    - A concurrent mutation landing during the commit transaction either serializes before it (and causes `preview_stale`) or after it; it never interleaves into a partial application.
    - Committing the same token twice with the same mutation identity returns the original stored result and performs no second write.
    - `keepling.preview_bulk_change` and `keepling.commit_bulk_change` both require `tasks.bulk` at the adapter and again at the application boundary; without it, both refuse and nothing is written.
    - A destructive single-target command — trash — is refused as a one-step tool call and is only reachable through preview and commit.
  </behavior>
  <action>
Create `Keepling.Adapters.Postgres.Preview` implementing the port. `commit/4` runs one
`Repo.transaction`: `SELECT ... FOR UPDATE` every target row in a deterministic identity order (so
two concurrent commits cannot deadlock), re-read every live revision, compare the whole set against
the token binding through `Preview.authorize_commit/2`, and only then apply every command through
the existing `Commands.dispatch/3` path so activity and undo handles are written exactly as they are
for a human client. Any mismatch returns `{:error, :preview_stale}` and the transaction rolls back
before a single write.

There is no code path that returns a per-target success list. If a result shape is tempting to
write that names which targets succeeded, that is the partial-success outcome D-18 forbids.

Register `keepling.preview_bulk_change` and `keepling.commit_bulk_change` in
`KeeplingWeb.MCP.Tools`. Preview takes the command, its arguments, and the resolved target
identities. Commit takes exactly two arguments: the token and a mutation identity. Commit must not
declare a target list in its schema — this is why the committed set cannot differ from the
previewed one. Both require `tasks.bulk`.

Route trash, restore, and undo away from any one-step tool: a call naming a destructive command
outside the preview and commit pair is a closed argument error.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP host → `keepling.commit_bulk_change` | An opaque token crosses here and is the sole authorization for a multi-target write |
| Preview time → commit time | The drift boundary; live state is authoritative, the token is only a claim |
| Commit transaction → Postgres | Atomicity boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-33 | Tampering | preview token | critical | mitigate | HMAC-SHA256 over a deterministically encoded closed field list, constant-time compare, `[:safe]` decoding, account re-checked after decode; a flipped byte fails |
| T-05-34 | Tampering | commit target set | critical | mitigate | Commit's generated schema declares exactly two properties and no target list, so the committed set is structurally the previewed set |
| T-05-35 | Tampering | partial write on drift | critical | mitigate | One transaction, `SELECT ... FOR UPDATE` in deterministic identity order, full-set revision recheck before any write; no per-target success shape exists to return |
| T-05-36 | Spoofing | cross-instance or cross-epoch token replay | high | mitigate | Server instance and sync epoch are binding fields compared by exact map equality, mirroring `SyncFeed.authorize_namespace/2` |
| T-05-37 | Repudiation | committed bulk change | high | mitigate | The commit applies through `Commands.dispatch/3`, so every target gets the same activity record and undo handle a human-issued change gets |
| T-05-38 | Denial of Service | oversized preview | medium | mitigate | `@maximum_targets` refuses rather than truncates; a fifteen-minute expiry bounds how long a token is live |
| T-05-39 | Elevation of Privilege | destructive one-step call | high | mitigate | `@destructive_commands` is closed and testable; a destructive command outside the preview and commit pair is a closed argument error |
| T-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package-manager install occurs in this plan. Any future install proposal requires the package-legitimacy gate and a blocking human checkpoint first |
</threat_model>
