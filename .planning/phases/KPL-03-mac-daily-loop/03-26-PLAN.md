<design_guidance>
## The evidence that reframes the problem

03-UAT.md's root_cause hypothesis was "A8 registers a rival global shortcut, and A9 inherits it".
That is a per-pair theory. It cannot explain today's failure, because today's failure is A1 — the
first row of the run, with no preceding row to inherit from. So either the leak crosses RUNS, or it
is produced by something the harness itself does before row 1, or both. Treat "the state a row runs
in is not the state it assumes" as the class, and stop guessing which row.

## Two leak paths the current file structurally permits

Read `restoreSystemSettings` and the `settingsState` block before designing anything, and note two
properties that are true today by construction, not by accident:

1. **Restoration is exit-scoped, not row-scoped.** `selectInputSource` (used by the non-US layout
   row) and `applySystemSettings` (used by the appearance/contrast/transparency/motion rows) mutate
   real system state, and the only restore is registered on process exit and signals. Between rows,
   whatever the last row set is still set. A non-baseline keyboard layout is exactly the machine
   state that turns a typed ASCII sequence into different characters — and "timed out waiting for
   the typed title to reach the capture field" is precisely what that looks like from inside the
   assertion.
2. **A leaked state is laundered into the next run's baseline.** `captureSystemSettings` runs once
   per process, records whatever it finds, and treats it as the value to restore to. If a previous
   run was killed before restoring, the next run captures the LEAKED state as its own baseline,
   restores to it at the end, and reports `restore=VERIFIED` — a correct-looking green over a
   machine that is no longer in its original condition. `settings-capture.json` is written but never
   removed after a verified restore, so today it is not usable as a marker; make it one.

Neither observation is a fix on its own. Both are things the barrier must be able to SEE.

## Teardown that finishes, not teardown that starts

`quitApplication` sends SIGTERM, waits for the spawned child to be reaped, and returns. Being reaped
is not the same as being gone from the window server or the accessibility session, and it is not the
same as some other application having become frontmost. The next row's `ensureFrontmost` then races
a teardown that is still in progress. Wait for the observable condition — no window belonging to
that pid remains in the accessibility/window list — rather than for the process table.

## Why mid-sequence focus theft matters more than it sounds

`postKeys` asserts frontmost once, then hands a whole sequence to the probe. If focus is lost after
that check, every remaining keystroke goes somewhere else, silently, and the failure surfaces 24
seconds later as a timeout in an unrelated assertion. That is why the same underlying event reports
as a different row each time. Make the loss itself the failure, named, at the moment it happens.

## Proving a race is fixed

One green run proves nothing about a race. Two consecutive full runs plus one seeded shuffled-order
run is the fixed, declared-in-advance budget for this plan. Do not increase it after seeing results,
and do not decrease it. The gate's `runLane` already carries a `seed` field for exactly this kind of
claim.
</design_guidance>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer's real machine -> lane process | The lane mutates real system accessibility settings and the active keyboard layout on a person's own Mac |
| lane run N -> lane run N+1 | State written by one run is read as baseline by the next |
| packaged artifact -> recorded evidence | A run's result is recorded as a durable claim about specific bytes |
