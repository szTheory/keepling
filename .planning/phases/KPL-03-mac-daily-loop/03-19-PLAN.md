<design_guidance>
Facts established before this plan was written -- verify them, do not assume they
are still true at the line numbers given:

* `DesktopPresentationInput` declares `{ kind: 'offline'; lastSuccessfulContact?: string }`
  at `presentation.ts:35`, and `deriveDesktopPresentation` maps it to
  'Offline — showing tasks saved on this Mac' at `presentation.ts:89-90`.
  `git grep "kind: 'offline'"` finds exactly two hits: that declaration and
  `test/application/recovery-presentation.test.ts:23`. There is no production
  construction site.
* `DesktopApplication.runSyncPass()` publishes `{ kind: 'updating', startedAt }`,
  then settles into `healthy` or `local_saved` on success and
  `retryable_failure` on ANY thrown error -- one catch block, no discrimination.
* `main/index.ts` builds a `realSync` whose `pull`/`push`/`acknowledge` each
  return an empty/null result when `syncAdapter === null` (no server
  configured). Those are RESOLVED promises, not throws, so a pass against an
  unconfigured app completes with `pulled: 0, settled: 0` and settles into
  `healthy` -- a row whose copy is null and which the UI presents as the quiet
  everything-is-fine state.

Three distinct situations currently collapse into two rows. Separate them:

1. **No server configured.** Nothing to be offline FROM. The app is working
   exactly as intended and its data is safe locally, but it is not
   synchronized and must never imply that it is. Decide deliberately between
   the existing `local_saved` row and `offline`, and record the reasoning --
   `healthy` is the one answer that is clearly wrong. Prefer the row whose copy
   a user would read as true.
2. **Server configured but unreachable.** This is `offline`. DNS failure,
   connection refused, TLS failure, a request timeout, `fetch` rejecting --
   the request never got an answer.
3. **Server answered, and the answer was a problem.** This stays
   `retryable_failure`. A 500, a malformed body, a bounded-page violation.

The discriminator must come from the adapter layer, which is the only layer
that knows whether bytes came back. Do not sniff error message strings in
`DesktopApplication` -- message text is not a contract and will drift. Give the
transport a way to say "unreachable" explicitly (a typed error, a tagged
result, or an equivalent) and have the application read that tag. Keep
`DesktopApplication` transport-agnostic: it must not import `fetch` semantics.

`lastSuccessfulContact` needs a source. The moment of the last successful
server contact is not currently recorded anywhere. Persist it where a relaunch
can still read it -- the local store already holds sync state (`syncState()` /
its cursor) and is the natural home. A never-contacted app reports null, and
the copy must read correctly with the field absent.

For Task 3 (O-28): the vitest suites were swept on 2026-09-03 and were clean --
every negation there is guarded by an adjacent positive assertion or by a read
that throws. The Playwright `test/e2e/**` and `test/packaged/**` suites were
NOT swept. The defect shape: `expect(text).not.toContain('X')` passes when
`text` is empty because the pane never rendered, so a slow window produces a
false PASS rather than a flake. The fix is to first assert the surface STATED
something -- wait for the positive condition that proves it rendered -- and
only then assert the negation. Enumerate every site you find, state its
verdict, and name any you judge already safe and why.
</design_guidance>
