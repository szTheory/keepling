## Why these rows are automatable

`accessibility.spec.ts` tests the DOM/ARIA layer inside Chromium. It genuinely cannot see
VoiceOver, real keystrokes, or system settings, and the contract concluded "human only". But the
missing layer is macOS, and macOS exposes all of it:

| Rows | Mechanism |
|---|---|
| A1-A4 | Do not drive VoiceOver. Read the **AXUIElement** tree of the running app — that is the data VoiceOver speaks. Assert `AXRole`, `AXTitle`, `AXValue`, `AXFocusedUIElement`, `AXSelected`. |
| A5-A6 | `defaults write com.apple.Accessibility FullKeyboardAccessEnabled` plus **CGEvent** posting — real OS-level key events, unlike Playwright's synthetic DOM events. |
| A7 | Set the input source, post the dead-key CGEvent sequence, assert the composed character in `AXValue`. |
| A8 | Spawn a second process that registers the same global accelerator, then fire it. Genuine OS arbitration. |
| A9 | Launch a real app, place a caret, invoke Quick Entry, assert frontmost app and restored `AXSelectedTextRange`. |
| A10-A15 | `defaults write` on `com.apple.universalaccess` / `com.apple.Accessibility` / `AppleInterfaceStyle`, then assert **computed WCAG contrast from rendered pixels** rather than "looks legible". |

Swift is used because `ApplicationServices` and `CoreGraphics` are the native homes of these APIs,
`swiftc` is already present (Xcode 26, Swift 6.3.3), and Phase 4 introduces a SwiftUI client anyway.

**The one irreducible human cost** is granting the test runner Accessibility permission in System
Settings → Privacy & Security → Accessibility. SIP protects the TCC database, so this cannot be
scripted. It is a one-time approval that then persists. The lane must fail with that exact
instruction when the permission is absent — never skip.
