<design_guidance>
## Task 1 — O-41: only capture_task can reach the wire

Verified: `type: 'capture_task'` at DesktopApplication.ts:259 is the ONLY
command type desktop production code constructs, and there is no production
`enqueue` call site anywhere in main/, store-worker/ or renderer/.
DesktopApplication.editTask (:295), applyLifecycle (:307) and moveToday (:314)
write the local store and return a WorkspaceSnapshot. Nothing goes out.

Follow the capture path exactly -- it is proven end to end by 03-21 and is the
reference implementation. Whatever capture does to become durable, survive a
hard kill, retry byte-identically and settle on an exact receipt, these must do
the same way. Do not invent a second mechanism.

The server already accepts these command types; nothing on the wire changes.
Check the contract's command enum for the exact type names and bodies, and note
03-21's finding that the desktop's durable bytes had omitted the
contract-required `version` -- do not repeat that.

Ordering matters and is the part most likely to be got wrong: an edit to a task
whose capture has not yet been acknowledged must not overtake it. State how you
handle that, and prove it rather than asserting it.

## Task 2 — O-38: the client cannot hear a conflict

adapters/sync.ts:90-94 accepts only `accepted`/`already_satisfied` and throws
`server acknowledgement is invalid` on anything else. The contract publishes
`conflict` and `rejected` (keepling.yaml:1392) and the server genuinely persists
conflicts (command_store.ex:707). So a real conflict crashes the adapter.

Both halves, or neither:
  (a) the adapter accepts the outcomes the contract publishes, and
  (b) `{ kind: 'conflict' }` and `{ kind: 'rejected' }` are actually constructed
      and published, so the authored copy reaches a person.

store-worker/local-store.ts:385 already builds conflict records when it sees a
conflict outcome -- that branch is live code that has never been reachable.
Prefer wiring it to rewriting it.

## Task 3 — O-42: every recovery action is discarded unread

SyncStatusRow reads only summary.copy and summary.kind. preload/contracts.ts:33
validates a max-3 action array that nothing reads. Render the actions and
dispatch them. The signed-out case is the clearest: today a person is told to
sign in with no way to do it from that surface.

`inspect`, `retry`, `sign_in`, `export`, `remove_local_data`, `retry_save`,
`retry_opening`, `show_recovery_options` ride on production-reachable states and
must all work. `check_again`, `review`, `review_conflict` become reachable via
Task 2.

## Task 4 — O-31(a): Quick Entry and Settings show nothing

These windows load a DIFFERENT, deliberately narrow preload bundle
(preload/utility-preload.ts, exposing window.keeplingUtility). `window.keepling`
and subscribePresentation do not exist in their JS context, so this is a new
validated IPC channel plus publisher wiring to those WebContents -- not a
component mount. Follow the existing presentation channel's schema-validated
pattern; keep the utility bridge as narrow as it is today.

Scope: desktop utility windows ONLY. apps/web has no synchronization concept at
all and is explicitly OUT of scope -- MAC-04 is a Mac requirement.
