## Why a predicate is not enough

The obvious version of this -- "if it is still in the outbox, drop it" -- is
WRONG, and the reason is the whole plan. `outbox` is
`(mutation_id, sequence)` (migrations/0001_initial.sql:49-52). A row sits there
unchanged while its POST is in flight, so the table cannot distinguish a command
that never left from one the server is accepting right now. Dropping the latter
means the server holds a command the client deleted.

So: explicit state. A row is `queued` until the moment before its bytes are
transmitted, `in_flight` from then until the outcome is known, and returns to
`queued` on a TRANSPORT failure (not on a decided refusal -- 03-22 made those
terminal, and that must not change). Undo may drop only `queued`.

Choose the state vocabulary deliberately and write down why. If a crash can
leave a row `in_flight` with no outcome, say what happens on next open -- an
`in_flight` row at startup is exactly the "uncertain" case the codebase already
has vocabulary for, and it must not be silently reset to `queued`.

## Task 1 — the migration runner

local-store.ts:934-949 is hardcoded to version 1 with a checksum binding.
Generalise it to apply an ordered set of migrations, preserving that binding: a
recorded checksum that does not match must still fail loudly. This is
infrastructure the project will need again; do it properly rather than
special-casing version 2.

Prove an existing pre-0002 database opens, migrates, and keeps its tasks AND
its queued commands. test/packaged/daily-loop.spec.ts already opens a retained,
already-migrated database -- that is the shape of proof wanted.

## Task 2 — undo of a never-transmitted mutation

Reverting the visible projection is already implemented. What is new is
removing the command so a later-configured server never flushes it. Reuse
03-22's resource key so an undo cannot race the mutation it undoes.

The refusal path 03-23 built stays for everything else: acknowledged mutations
use the handle, an `in_flight` command is refused with honest copy, and a
missing handle is still a loud refusal rather than a silent local undo.

## Task 3 — prove the case that motivated this

An app with NO server configured: capture, edit, undo, and the undo takes
effect. Then prove the dangerous case directly -- a command in flight cannot be
dropped by an undo racing it. Prove that against real behaviour, not by
asserting a branch was taken.
