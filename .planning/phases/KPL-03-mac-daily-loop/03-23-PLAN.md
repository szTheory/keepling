<design_guidance>
## Why this is not another buildOutboundCommand case

03-22 wired six command types by constructing durable bytes and letting the
outbox carry them. Undo cannot be done that way and 03-22 correctly refused to
pretend otherwise: `POST /commands/undo-task` takes a SERVER-ISSUED handle,
carried in the `undo` field of the CommandAcknowledgement, and this client
retains it nowhere. So the work is:

  1. persist undo handles alongside the mutation journal as acknowledgements
     arrive, with expiry, and
  2. enqueue an undo command that references a retained handle.

Read the contract for the handle's shape, lifetime and expiry semantics before
designing the storage. Do not guess them.

## The case that matters most

An undo performed while OFFLINE, against a mutation whose own acknowledgement
has not arrived yet, so no handle exists to reference. Decide what happens and
prove it. Options include refusing the undo at the point of action with honest
copy, or deferring it until the handle lands. Both are defensible; silently
accepting it locally and dropping it is not, and is the defect being fixed.

Ordering interacts with 03-22's resource key: an undo of a task must not
overtake the mutation it undoes. Reuse that mechanism rather than adding a
second one.

## Expiry

Handles expire server-side. An undo referencing an expired handle must surface
as a decided refusal through the path 03-22 built for 409/422 -- reuse
classifyServerRefusal rather than adding a parallel branch. Check whether the
server's expiry code is already in REJECTION_CODES; add it there if not.

## Scope discipline

O-43 (a refused local change has no durable home), O-46 and O-47 (preparing and
uncertain still unconstructed) are OUT of scope and must stay open. If closing
O-45 turns out to require a decision on any of them, STOP and report rather
than deciding it inside this plan.
</design_guidance>
